# MPLADS Anomaly Investigation System

Explainable anomaly detection over real MPLADS data. Seven statistical signals,
a transparent 0–100 continuous risk score, and a React dashboard where every
flagged work shows its exact reasoning and comparable evidence.

```
data/raw/          →  pipeline/detect_anomalies.py  →  backend/mplads.db  →  FastAPI  →  React
(6 source CSVs)       (scoring + DB build)              (SQLite)              (:8000)    (:5173)
```

## Quick start

```bash
# 1. Run the scoring pipeline and build the database (~30 s)
python3 pipeline/detect_anomalies.py

# 2. Start everything
./run.sh
#    API  →  http://localhost:8000
#    UI   →  http://localhost:5173
```

Or start services individually:

```bash
./run.sh --pipeline-only   # re-score and rebuild DB only
./run.sh --backend-only    # API only (needs existing mplads.db)
./run.sh --frontend-only   # UI only (needs running API)
```

## Login credentials

The dashboard requires authentication. Default accounts:

| Username | Password | Role |
|----------|----------|------|
| `admin` | `admin123` | Administrator |
| `analyst` | `analyst123` | Senior Analyst |
| `auditor` | `auditor123` | Audit Officer |

Sessions are stored in `localStorage` and validated against the backend on page load.
To change credentials, edit the `_USERS` dict in `backend/main.py`.

New accounts can be created from the **Sign Up** link on the login page. A role must be chosen during registration; new accounts are active immediately.

## Risk scoring

Seven independent signals are each normalised to a fixed point budget, then summed.
The empirical worst case in this dataset is mapped to 90, preserving relative ordering.

| Signal | Max pts | What it measures |
|---|---|---|
| Financial Anomaly | 25 | Cost z-score vs category peers (tanh curve) + MP spend concentration |
| Unaccounted Funds | 20 | Expenditure disbursed but work not completed, or payment >> completed amount |
| Stalled Work | 20 | Sanctioned work stuck at early status for >180 days |
| Recommendation Delay | 10 | Rec→sanction too fast (<2 days, rubber-stamp) or too slow (>180 days, bureaucratic hold) |
| Phantom Completion | 10 | Work marked complete 0–3 days after sanction (physically implausible) |
| Duplicate Work | 10 | Same MP, near-identical description, similar amount |
| Calamity Fund Misuse | 5 | MP received calamity consent but works not in disaster-relief categories |

Theoretical max = 100. Scores are continuous (not bucketed).

## Risk tiers

| Tier | Range | Meaning |
|---|---|---|
| Baseline | 0–19 | No significant signals |
| Medium | 20–39 | One or two weak signals — periodic review |
| High | 40–74 | Multiple compounding signals |
| Critical | 75–100 | Severe or overlapping signals — priority investigation |

## API endpoints

| Endpoint | Description |
|---|---|
| `GET /api/overview` | Dashboard KPIs including estimated financial exposure |
| `GET /api/filters` | Available filter values |
| `GET /api/works` | Paginated, filtered, sorted works |
| `GET /api/works/{id}` | Work detail with full evidence breakdown |
| `GET /api/works/{id}/peers` | Comparable works in same category |
| `GET /api/works/{id}/related-transactions` | Same MP's transactions in same category |
| `GET /api/documentation-gaps` | MPs with high proportions of missing verification photos |
| `GET /api/mps/top-suspicious` | Top MPs by flagged work count |
| `GET /api/mps/{name}` | MP profile with risk summary |
| `POST /api/ai-search` | Natural language project search (requires GROQ_API_KEY) |

### AI search (optional)

Set `GROQ_API_KEY` in `backend/.env` to enable natural language search:

```bash
GROQ_API_KEY=your_key_here
GROQ_MODEL=qwen/qwen3.8-27b   # or any Groq model with JSON mode
```

Example queries:
- "Find critical road projects in Karnataka above ₹20 lakh"
- "Show stalled works sanctioned before 2023"
- "Find phantom completions above ₹50 lakh"

## Design notes / honest limitations

- **No vendor field** in the source data. `IDA` is a government district office,
  not a contractor, so vendor-concentration is implemented as MP category-spend
  concentration instead.
- **No project start date** exists, only a completion/payment date, so a
  duration-delay signal was not built rather than faked.
- **Expenditure transactions carry no Work_ID**, so "related transactions" on a
  flagged work are the same MP's other transactions in the same category —
  clearly labelled as such in the API response.
